Part A – Understand

A1 What BulkReg does

Directory Sync (DirSync) copies Active Directory users into the Domino Directory (names.nsf) as Person documents. These users can be found in Domino, but they have no Notes ID, no certificate and no mail file (Mail system: Other Internet Mail).

BulkReg turns them into full Domino users, in reviewed batches. Each user gets a certified Notes ID, which is stored in the ID Vault, and a Domino mail file on the right home server. The Person document then points to that mail file. Every step is logged for audit.

It uses HCL's documented API for this case, NotesRegistration.ContactNoteID: “Used to register users who have existing Person documents created by syncing Active Directory users into the Domino directory.” The existing Person document is upgraded in place, so no duplicate is created.

A4 Organizational or explicit policy: which one assigns the vault?

The ID reaches the vault because the user's effective policy includes a Security Settings document that assigns the vault. HCL: “If you create an organizational policy, it automatically applies when you register users. If you create an explicit policy, you assign it manually during user registration, in the Person document or by using the Policy Assignment tool.”

B3 Confirm that DirSync users exist

Who: Domino administrator Where: Domino Administrator Changes: nothing

  1. In Domino Administrator, select the registration server in the server pane.
  2. Click the People & Groups tab, then Domino Directories > (your directory) > People. Result: a list of Person documents.
  3. Select a user you know was synchronized from Active Directory.
  4. Click File > Document Properties, then the Fields tab (the second tab in the properties box).
  5. In the left column, scroll to objectGUID and click it. Result: a value is shown on the right. This marks a DirSync Person document.
  6. Scroll to Certificate. Result: the field is missing or empty. This means the user is not registered yet.
  7. Scroll to MailSystem, MailFile and MailServer and note their values. After registration they will point to the new Domino mail file.
Done when
At least one Person document has an objectGUID value and no Certificate.

B4 Give your admin ID directory access

Who: Domino administrator with Manager access to names.nsf Where: Domino Administrator Changes: the names.nsf ACL on the registration server

HCL: UserCreator lets administrators create Person documents, and UserModifier lets them edit them. Editor access already allows editing.

  1. In Domino Administrator, select the registration server in the server pane.
  2. Click the Files tab and select names.nsf (the Domino Directory).
  3. In the Tools pane, choose Database > Manage ACL. Result: the Access Control List dialog opens.
  4. If your admin ID (or a group it belongs to) is not listed, click Add, enter the name and click OK.
  5. Select the entry and set Access to Editor.
  6. Make sure Create documents and Delete documents are ticked. Registration creates and updates documents.
  7. Click Roles and tick [UserCreator] and [UserModifier]. If you will create the policy yourself (B7, B8), also tick [PolicyCreator] and [PolicyModifier].
  8. Click OK to save the ACL.
  9. Wait for the ACL change to reach the server you work on. It is immediate on the registration server itself.

Create the numbered mail folders on every home server

Create the mail subfolders in advance on every home server, so registration never depends on Domino creating a folder. You need one folder per 1000 users (MailFilesPerFolder) on each server:

Users on that home serverFolders to createNames
1 – 1,0001mail1
5,0005mail1 … mail5
10,00010mail1 … mail10
NN ÷ 1000, rounded upmail1 … mailN
Note
If the folders already contain mail files, you may need more. After B11/B12, Preflight (C1) calculates the exact number per server, counting the existing files, and writes the commands to C:\BulkReg\audit\BulkReg_Preflight_<run>_mailfolders.txt. Create any extra folders it lists.
  1. Find the Domino data directory of the home server. It is the Directory= setting in that server's notes.ini, for example D:\Domino\Data (Windows) or /local/notesdata (Linux). In Domino Administrator, select the server; the Files tab shows its contents.
  2. Sign in to the server's operating system as an administrator (Windows) or as root (Linux).
  3. Create the folders. Replace <DataDir> and the number (here 5):
Windows server (PowerShell as Administrator):
  1..5 | ForEach-Object { New-Item -ItemType Directory -Force "<DataDir>\mail$_" }

Linux server (as root; notes = the OS account that runs Domino):
  for i in $(seq 1 5); do mkdir -p <DataDir>/mail$i; done
  chown notes:notes <DataDir>/mail*
  chmod 755 <DataDir>/mail*
  1. On Windows, make sure the account that runs the Domino service has Modify rights on the new folders. They normally inherit from the data directory.
  2. In Domino Administrator, select the server and open the Files tab. Press F9 to refresh. Result: mail1 … mail5 appear in the folder list.
  3. Repeat for every home server, using its own number of folders.
  4. Write the number of folders you created into the worksheet (row 11d). It goes into MailFolderMax in B11. Use the lowest number created on any server, or create the same number on all servers.

Allow your admin ID to create mail files on every home server

  1. In Domino Administrator, click the Configuration tab and open Server > All Server Documents.
  2. Open the Server document of the first home server (worksheet row 3) and click Edit Server.
  3. Click the Security tab. In Create databases & templates, make sure your admin ID (or a group it belongs to) is listed, or that the field allows everyone your policy permits.
  4. Click Save & Close. Repeat for every home server.
  5. Check that the mail template from worksheet row 11b exists on every home server (Files tab of each server, filter on .ntf).
Done when
Your admin ID has Editor access with [UserCreator] and [UserModifier] (and the Policy roles if needed) in names.nsf. The numbered mail folders exist on every home server. Your admin ID can create databases there, and the mail template exists on each of them.

B5 Set up certification

Choose one option (worksheet row 5). Option 1 (Domino CA) is recommended: no certifier password is needed during a run.

Option 1 – Domino server-based CA: add your admin ID as a Registration Authority

Who: CA administrator Where: Domino Administrator + server console of the CA server Changes: the CA certifier (RA list)

  1. Open the console of the server that hosts the CA: in Domino Administrator, select that server, click the Server tab, then Server Console.
  2. Type tell ca stat and press Enter. Result: the CA process answers and lists its certifiers. If it is not running, type load ca first.
  3. Type tell ca quit and press Enter (required before modifying the certifier).
  4. Click the Configuration tab. In the Tools pane choose Certification > Modify Certifier.
  5. Select the server that hosts the CA, then select the certifier from worksheet row 6.
  6. In the Certifier dialog, add your admin ID (worksheet row 12) as a Registration Authority (RA) and click OK.
  7. On the console type tell adminp process all, then load ca, then tell ca refresh, then tell ca stat. Result: the certifier is listed, with your RA change in place.
Note
HCL reference: “Modifying a server-based CA” (Appendix C). The CA process must be restarted after a server restart unless ca is in the ServerTasks setting.

Option 2 – Certifier ID file

  1. Obtain the certifier ID file and its password from the certifier owner, following your organisation's handover process.
  2. Copy the file into C:\BulkReg\cert\ after you create the folders in B9. Do not put it anywhere else.
  3. Write down its path for B11. Never write the password into a file. BulkReg asks for it in a masked dialog at run time.
Done when
Option 1: tell ca stat shows the certifier and your ID is an RA. Option 2: you have the certifier ID file and its owner has given you the password.

B6 Create the ID Vault (skip if you already have one)

Who: Domino administrator with Create databases access on the vault server and Editor access to names.nsf Where: Domino Administrator Changes: creates the vault database and vault document

  1. In Domino Administrator, click the Configuration tab.
  2. Choose Tools > ID Vaults > Create. Result: the ID vault wizard starts.
  3. Enter the vault name from worksheet row 7. HCL: it cannot be the same as an organization or OU name, and it cannot be changed later.

  6. Add at least one vault administrator.

B7 Create the Security Settings document

Who: Domino administrator with [PolicyCreator] Where: Domino Administrator Changes: creates one settings document in names.nsf

This document tells Domino to put each registered user's ID into the vault, and sets the password rules. Create one per vault if you have several.

  1. Click the People & Groups tab, then open the Settings view.
  2. Click Add Settings and choose Security. Result: a new Security Settings document opens.
  3. On the Basics tab, enter the Name from worksheet row 8 and a Description, for example: Assigns DirSync users to the ID vault.
  4. Click the ID Vault tab. In Assigned vault, select the vault from worksheet row 7.
  5. Leave Enforce password change after password has been reset set to Yes (default).
  6. Click the Password Management tab and set your organisation's password rules (for example Required change interval and Allowed grace period).
  7. To force a password change at first login: set Use custom password policy for Notes clients to Yes. Then, on the Custom Password Policy tab, enable Change password on first Notes client use. HCL: this works only if the policy is applied during user registration, which BulkReg does.
  8. Click Save & Close.
Done when
The Security Settings document is listed in the Settings view, and its ID Vault tab shows your vault.

B8 Create the policy that assigns the vault

Choose Option A (explicit) or Option B (organizational) using A4. Write your choice in worksheet row 9.

Option A – Explicit policy (only the users BulkReg registers)

Who: Domino administrator with [PolicyCreator] Where: Domino Administrator Changes: creates one policy document in names.nsf

  1. Click the People & Groups tab, then open the Policies view.
  2. Click Add Policy. Result: a new Policy document opens.
  3. In Policy name, type the name from worksheet row 9 without */, for example DirSync-Vault.
  4. Set Policy type to Explicit.
  5. Enter a Description, for example: BulkReg – DirSync users, ID vault DirSyncVault.
  6. In the Security settings field, select the Security Settings document from B7. Press F9 if it is not listed.
  7. Leave the other settings types empty unless your organisation requires them.
  8. Click Save & Close.
  9. Look at the Policies view. HCL: Domino stores an explicit policy as */policyname, so the policy is listed as */DirSync-Vault. Copy this exact name into the worksheet. You will use it in bulkreg.ini and server_mapping.csv.
  10. Repeat B7 and B8 for every additional vault or region.
Caution
BulkReg passes the policy name to NotesRegistration.PolicyName. Use the name exactly as the Policies view shows it (with */). The pilot (C5) confirms it: Person document > Policy synopsis must show this policy.

Option B – Organizational policy (everyone under an org or OU)

  1. Click the People & Groups tab, then open the Policies view.
  2. Check whether a policy for your org or OU already exists (for example */Demo or */Sales/Demo). If it does, edit it in step 6 instead of creating a new one.
  3. Click Add Policy.
  4. In Policy name, type the organization or OU without */, for example Demo or Sales/Demo.
  5. Set Policy type to Organizational.
  6. In the Security settings field, select the Security Settings document from B7. Press F9 if it is not listed.
  7. Click Save & Close. Result: the Policies view lists */Demo (or */Sales/Demo).
  8. In bulkreg.ini set OrgPolicyAssignsVault=1 and leave DefaultPolicy= empty (B11). In server_mapping.csv, put - in the Policy column of the rules that rely on it (B12).
  9. If you use an OU policy (*/Sales/Demo), make sure the mapping gives those users OrgUnit Sales, so they are registered as John Smith/Sales/Demo.
Done when
Option A: each explicit policy is listed, linked to a Security Settings document with the right vault, and its exact name is in the worksheet. Option B: the organizational policy is listed, linked to that Security Settings document, approved, and OrgPolicyAssignsVault=1.

D3a Mail files: naming, uniqueness and folders

Every user BulkReg registers becomes a Domino mail user: registration creates a mail file on the user's home server and the Person document points to it (MailServer, MailFile, Mail system = Notes). Agent 02 decides each mail file's name and folder while it builds the batch, and records the decision so you can review it before anything is created.

1. Name = last name

MailFileNamingJohn SmithAnna MüllerSeán O'Brien
LASTNAME (default)smith.nsfmueller.nsfobrien.nsf
FIRSTINITIAL_LASTNAMEjsmith.nsfamueller.nsfsobrien.nsf
SHORTNAME<ShortName>.nsf (last name if empty)

Names are lower case. Accents are converted (ä→ae, ö→oe, ü→ue, é→e, ß→ss…), and only a–z, 0–9, _ and - are kept.

2. Uniqueness on each home server

A name counts as taken on a home server if it is found in any of these, checked in this order:

SourceHow it is checked
Files on the serverAgent 02 reads the server's database list once per run and records every file in folders starting with the prefix (mail, mail1, mail2 …)
Person documentsEvery Person document with a MailFile (and its MailServer) in the Domino Directory
Open batchesMail files reserved by other OPEN batch files
This batchRows already allocated earlier in the same batch

If the name is taken: with MailFileCollision=SUFFIX (default) the next free name is used (smith2.nsf, smith3.nsf …) and the row is marked WARN: mail file renamed. With ERROR the row gets Check=ERROR and Include=N. Uniqueness is per home server and across all its mail folders, so the same name is never used twice on one server. Agent 03 checks again just before registering that the exact file does not exist, so an existing mail file is never overwritten.

3. Numbered folders: mail1, mail2 …

With MailFolderMode=NUMBERED (default), mail files go into numbered subfolders of the data directory: mail1, mail2, mail3 …. Each holds at most MailFilesPerFolder (default 1000). Files already in those folders are counted, per home server, and so are open batches. A folder is filled before the next one is used.

Situation on DominoADMail/DemoBatch of 500 users gets
mail1 has 980 mail files20 users → mail1 (now 1000), 480 users → mail2
mail1 and mail2 full, mail3 has 300500 users → mail3 (now 800)
No mail folders yet500 users → mail1

The folders must already exist on the servers (prerequisite B4). MailFolderMax is the number of folders you created. If a user would need a folder above it (for example mail6 when you created mail1–mail5), Build Batch marks the row ERROR: all pre-created mail folders are full instead of creating a new folder. Create the next folder, raise MailFolderMax and rebuild.

With MailFolderMode=SINGLE, all mail files go into MailFileDir (for example mail).

D8 Rollback

Registration certifies the existing Person document and creates an ID. It cannot be cleanly undone, which is why the dry run and the pilot exist. To reverse users, take them from BATCH-<id>_results.csv and use your standard deletion process (AdminP Delete Person) and vault clean-up. HCL notes that users registered through user registration are not removed by a DirSync full resync. To recover from an interrupted run, build a new batch: the unregistered users are offered again.
