1. Overview

1.1 What BulkReg does

Directory Sync (DirSync) copies Active Directory users into the Domino Directory as Person documents. These users have no Notes ID, no certificate and no mail file (Mail system: Other Internet Mail). BulkReg registers them in reviewed batches. Every user gets a certified Notes ID, the ID is placed in the ID Vault, and the user is assigned to the right home server among your Domino servers. Every action is logged and auditable.

BulkReg uses HCL's documented API for this case, NotesRegistration.ContactNoteID: “Used to register users who have existing Person documents created by syncing Active Directory users into the Domino directory.” The existing Person document is upgraded in place.

1.2 You always know who will be registered

Registration never selects users on its own. It is a three-stage process:

StageAgentWhat happensChanges data?
1 Build02 | Build BatchSelects the next batch (default 500) of unregistered DirSync users. Resolves each user's home server, OU, policy, groups and vault. Validates them and writes BATCH-<id>.csv plus a summary per server.No
2 ReviewYou (Excel)Check the list. Set Include=N to leave someone out, or correct HomeServer / OrgUnit / Policy / Groups / VaultServer.No
3 Register03 | Register BatchLoads the batch file you choose. Shows the totals per home server. In LIVE mode you must type the batch ID to approve. It registers only rows with Include=Y, and only if the document's objectGUID still matches.Yes

2.2 What Agent 03 does for each approved row

  1. Loads the Person document by NoteID and checks that its objectGUID equals the value in the batch file. If not, the row is skipped.
  2. Re-checks that it has no Certificate. If it was registered in the meantime, the row is skipped (safe to re-run).
  3. Uses the reviewed HomeServer, OrgUnit, Policy, Groups, VaultServer from the batch file and validates them.
  4. Calls RegisterNewUser with ContactNoteID, passing the home server's canonical name. The explicit policy assigns the ID Vault, so the ID is deposited during registration.
  5. Confirms the Certificate now exists. Puts back the original Mail system (Other Internet Mail) if that is configured.
  6. Checks IsIDInVault on the row's vault server, then writes one row to BATCH-<id>_results.csv and to the audit log.

2.3 Built-in safety controls

6. Step 4 – Build the Tool Database (bulkreg.nsf)

Who: Domino administrator with Domino Designer. Changes: creates one local database.

  1. Create a blank local database bulkreg.nsf on the admin workstation. Set its ACL to administrators only.
  2. Optional: create bulkreg_log.nsf from the Agent Log template (alog4.ntf) for central logging.
  3. In Designer create a LotusScript library named exactly BulkRegCommon and paste in BulkRegCommon.lss.
  4. Create five LotusScript agents and paste in the matching file. For each one set Trigger: Action menu selection and Target: None, and keep Option Public, Option Declare and Use "BulkRegCommon" in (Options).
Agent name (exactly)Source file

7. Step 5 – Preflight (Agent 01)

Changes: none. Gives you the whole picture before you build any batch.

  1. Run 01 | Preflight Check.
  2. Read the summary: environment PASS/FAIL, OK / WARN / ERROR per user, and candidates per home server.
  3. Open C:\BulkReg\audit\BulkReg_Preflight_<run>_audit.csv. Fix data ERRORs in AD and let DirSync re-sync. Correct server_mapping.csv if users land on the wrong server.
  4. Use the per-server counts to plan batches: for example, one wave per home server (BatchServerFilter) or mixed batches of 500.
Done when
Environment errors = 0. You know how many users go to each home server, and you have a batch plan.

8. Step 6 – Build a Batch and Review It (Agent 02)

Changes: none in Domino. Writes the batch file you will approve.

  1. Optional: set BatchServerFilter=Mail02/ORG to build a batch for one home server only, or use ExtraSelection to limit it to a department or wave.
  2. Run 02 | Build Batch. It reports the batch ID, for example BATCH-20261005-093000.
  3. Open C:\BulkReg\batches\BATCH-<id>_summary.txt: rows, Include=Y, ERRORs, users per home server and per policy, and how many users are left for the next batch.
  4. Open BATCH-<id>.csv in Excel and review it (chapter 14 explains every column):
  5. Leave a user out by setting Include=N. Change HomeServer / OrgUnit / Policy / Groups / VaultServer if needed. Do not change NoteID or objectGUID.
  6. Save as CSV UTF-8 (Comma delimited), keeping the same file name. Attach the reviewed file to the change ticket as the approval record.
Note
Rows with Check=ERROR are written with Include=N. Users in this batch will not be picked by the next Build Batch until this batch is DONE. To discard a batch you will not run, move its file out of the batches folder.
Done when
You have reviewed every Include=Y row, and the reviewed BATCH-<id>.csv is approved in the change ticket.

9. Step 7 – Dry-Run the Batch (Agent 03, DryRun=1)

Changes: none.

  1. Confirm DryRun=1. Run 03 | Register Batch and accept the proposed batch file (the newest open batch) or enter another path.
  2. Check the dialog: number of users, number excluded, and users per home server. Answer Yes.
  3. Open BATCH-<id>_dryrun_<run>.csv. Every approved user shows WOULD_REGISTER. Any SKIPPED or FAILED_VALIDATION rows need fixing (edit the batch file, or rebuild it).
Done when
All approved rows show WOULD_REGISTER. The batch is still OPEN.

10. Step 8 – Pilot Batch (2 Users)

Changes: registers 2 users. Do this once, before the first real batch.

  1. Set ExtraSelection=ShortName = "pilot1" : "pilot2" and run 02 | Build Batch. Alternatively, set Include=N on all rows except two in a normal batch.
  2. Set DryRun=0. Run 03 | Register Batch, answer Yes, type the batch ID, and enter the certifier password if UseCA=0.
  3. Check both users by hand: Certificate and hierarchical name, correct home server, Mail system still Other Internet Mail. The user can download the ID from the vault and log in.
  4. Run 04 | Verify and choose the pilot batch file. Then clear ExtraSelection and set DryRun=1 again.
Done when
Both pilot users are REGISTERED and IN_VAULT, and the manual checks pass.

11. Step 9 – Register the Reviewed Batch (Agent 03, LIVE)

Changes: registers the approved users.

  1. Set DryRun=0. Run 03 | Register Batch and choose the reviewed BATCH-<id>.csv.
  2. Check the totals per home server. Answer Yes and type the batch ID exactly.
  3. Watch progress in the status bar, or with bulkreg.cmd Tail. Keep the client open and the PC awake.
  4. At the end, read the summary: ok / failed / skipped. Results are in BATCH-<id>_results.csv, and the batch is now DONE.
  5. Set DryRun=1 again.
Note
If the circuit breaker stops the run, the remaining rows are recorded as NOT_PROCESSED and the batch is still marked DONE. Those users (and any FAILED ones) are offered again by the next Build Batch once the cause is fixed.
Done when
The batch is DONE, and every row in BATCH-<id>_results.csv has a result.

12. Step 10 – Verify the Batch and Close (Agent 04)

  1. Run 04 | Verify Registration + Vault and choose the batch file (the default is the newest batch). The report is BATCH-<id>_verify_<run>.csv.
  2. Every row should be REGISTERED with IN_VAULT. For NOT_IN_VAULT, check the policy and vault, then run Verify again later (replication).
  3. Hand over initial passwords (C:\BulkReg\secure\BulkReg_InitialPasswords_<batch>_<run>.csv) through an approved secure channel.
  4. Delete secrets only after Verify shows IN_VAULT: bulkreg.cmd PurgeSecrets -IncludeIds -Yes, or delete the files manually.
  5. Archive the batch, results, verify and audit files with the change record.
  6. Next batch: go back to Step 6.
Done when
The batch's users are IN_VAULT, the secrets are deleted, and the records are archived.

13. Registering Across Multiple Servers

13.1 How the servers fit together

RoleHow manyWhat BulkReg does with it
Registration serverOne per Domino domain (normally the admin server, which holds the Domino Directory master)All registrations run against it (RegistrationServer). The Person documents are updated there and replicate to the other servers.
Home serversAny numberEach user gets one, from server_mapping.csv, reviewable in the batch file. It is passed to RegisterNewUser as the canonical name and becomes the user's home/mail server.
ID Vault serversOne or more vaults, each with replicasThe policy decides which vault receives the ID. VaultServer (default or per mapping rule) is only where BulkReg checks IsIDInVault.
PoliciesOne per target groupMap users to the explicit policy whose Security Settings assign the right vault (and other settings for that group)

13.2 Plan the mapping

  1. List your home servers and which users belong on each (by department, email domain, location or company).
  2. Write one rule per group in server_mapping.csv, most specific first, with the catch-all last.
  3. Run Preflight (01). Check the candidates per home server counts and the MapRule column in the audit CSV.
  4. Adjust the rules until every user lands on the intended server, OU and policy.

13.3 Batch strategies

StrategyHowWhen to use
Mixed batchesBatchSize=500, no BatchServerFilter. Agent 03 shows users per server before you approve.Servers are similar and all are ready
One server per waveBatchServerFilter=Mail02/ORG, then Build → Review → Register. Repeat per server.Servers go live on different dates, or are owned by different teams
Department or region wavesExtraSelection=Department = "Sales" (any @formula)Business-driven rollout
Per-row overrideEdit HomeServer / Policy / VaultServer in the batch fileExceptions: individual users who need a different server

13.4 Multiple Domino domains or directories

BulkReg works within one Domino Directory per configuration. If you have several domains, use one config file per domain (DirectoryServer, RegistrationServer, certifier, mapping). Keep them as separate files, for example bulkreg-emea.ini, and enter the matching path when an agent starts.

18. Troubleshooting

To debug: set LogLevel=DEBUG, rebuild a small batch (for example ExtraSelection on one user), dry-run it, and read the debug log. FAILED rows show the stage (load, validate, configure, RegisterNewUser, verify, preserveMail, vault), the Notes error number and the code line.

SymptomLikely causeFix
Build Batch selects 0 usersAll users registered, already in OPEN batches, filtered by BatchServerFilter or ExtraSelectionCheck the summary's 'Not selected' line; finish or remove the open batches
"There is no open batch file"No batch built, or all batches are DONERun 02 | Build Batch
"already DONE"The batch already ran LIVEBuild a new batch; unregistered users are picked again
"header is missing … columns"The CSV was re-saved without its header, or with a different layoutRebuild the batch; save as CSV UTF-8
Rows SKIPPED: objectGUID mismatchThe Person document was recreated, or the row was editedRebuild the batch
FAILED_VALIDATION: HomeServerEdited HomeServer is empty or unreachableFix the batch row or the server
FAILED stage=RegisterNewUserNot an RA, wrong certifier or password, missing rights, unknown serverRead the debug log message; fix the CA/RA, certifier, rights or server name
REGISTERED_VAULT_PENDINGPolicy has no vault, wrong VaultServer for that vault, or replication delayCheck the policy synopsis and the mapping VaultServer; re-run Verify later
MailSystem changes after the next syncDirSync attribute mappingAdjust the DirSync mapping, or set PreserveMailSystem=0
Agent not in the Actions menu / refuses to runWrong trigger, not signed, or not in the Windows clientStep 4 settings; run from the Windows admin workstation

Escalate to the platform owner if failures affect more than one batch. Escalate immediately to the security owner if a password file, ID file or certifier may have been exposed.

19.3 Rollback

Registration certifies the existing Person document and creates an ID. It cannot be cleanly undone. To reverse users, take them from BATCH-<id>_results.csv and use your standard deletion process (AdminP Delete Person) and vault clean-up. HCL notes that users registered through user registration are not removed by a DirSync full resync. To recover from an interrupted run, build a new batch: the unregistered users are offered again.

Appendix A – Alternative Methods (Manual)

Agent 05 writes C:\BulkReg\secure\BatchReg_DirSync_<run>.txt (HCL's 20-field format, UTF-8 BOM, contains passwords). Import it with People → Register → Import Text File. HCL documents this for new users, so test 1–2 DirSync users first.
