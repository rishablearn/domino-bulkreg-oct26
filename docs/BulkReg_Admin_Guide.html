1. Overview

1.1 What BulkReg does

Directory Sync (DirSync) copies Active Directory users into the Domino Directory as Person documents. These users have no Notes ID, no certificate and no mail file (Mail system: Other Internet Mail). BulkReg registers them in bulk. Every user gets a certified Notes ID, the ID is placed in the ID Vault, and each user is assigned to the right home server. Every action is logged and auditable.

BulkReg uses HCL's documented API for exactly this case, NotesRegistration.ContactNoteID: “Used to register users who have existing Person documents created by syncing Active Directory users into the Domino directory.” The existing Person document is upgraded in place, so no duplicate entry is created and users keep their Other Internet Mail setting.

2. How BulkReg Works

2.1 Components

ComponentWhat it isRequired?
bulkreg.nsfSmall Notes database you create. It holds the library and four agents.Yes
BulkRegCommonLotusScript library: config, mapping, logging, audit, vault checkYes
Agent 01 – PreflightChecks the environment and every candidate. Read-only.Yes
Agent 02 – ExportWrites HCL's registration text file (Appendix A method only)Optional

bulkreg.ini / bulkreg.linux.iniSettings (no secrets)Yes
server_mapping.csvRules: which home server, OU, policy and groups each user getsYes (one line minimum)
bulkreg.sh / bulkreg.ps1Helper scripts for folder setup, checks and reporting (chapter 12)Optional

2.2 What happens to each user (Agent 03)

  1. Selects Person documents that have objectGUID and have no Certificate. This is HCL's documented rule for DirSync users.
  2. Applies the first matching rule in server_mapping.csv to get home server, OU, explicit policy and groups.
  3. Re-reads the document. If it was registered in the meantime, it is skipped (safe to re-run).
  4. Validates the data. Bad records are logged and skipped.
  5. Calls RegisterNewUser with ContactNoteID. The explicit policy assigns the ID Vault, so the ID is deposited during registration.
  6. Confirms the Certificate now exists. Puts back the original Mail system (Other Internet Mail) if that is configured.
  7. Checks IsIDInVault, then writes one audit row. If enabled, the initial password goes to a separate restricted file.

2.3 Built-in safety controls

ControlEffect

4. Step 2 – Prepare Working Folders

Who: Windows or Linux administrator. Changes: creates local folders. BulkReg writes ID files, initial passwords and audit logs to disk, so these folders must exist and two of them must be locked down.

FolderHoldsAccess
configbulkreg.ini, server_mapping.csvAdmins
idsID files created during registrationRestricted – admin (Mode A) or Domino service account (Mode B)
secureInitial-password file, registration text fileRestricted – same as ids
auditAudit CSVs, debug logsAdmins and auditors (read)
certCertifier ID (Mode A with UseCA=0 only)Restricted

Default base folder: C:\BulkReg\ on Windows and /local/bulkreg/ on Linux. Where: Mode A on the admin workstation; Mode B on the Domino server.

Option 1 – manual commands

Windows (elevated PowerShell):

$b = 'C:\BulkReg'
'config','ids','secure','audit','cert' | ForEach-Object { New-Item -ItemType Directory -Force "$b\$_" }
'ids','secure','cert' | ForEach-Object {
  icacls "$b\$_" /inheritance:r /grant:r '*S-1-5-32-544:(OI)(CI)F' '*S-1-5-18:(OI)(CI)F' "${env:USERDOMAIN}\${env:USERNAME}:(OI)(CI)F"
}
# Mode B on a Windows Domino server: also grant the Domino service account, e.g.
# icacls "$b\ids" /grant 'DOMAIN\svc-domino:(OI)(CI)M'   (same for secure, audit)

Linux / RHEL (as root; `notes` = the OS account that runs Domino):

mkdir -p /local/bulkreg/{config,ids,secure,audit,cert}
chown -R notes:notes /local/bulkreg
chmod 750 /local/bulkreg /local/bulkreg/config /local/bulkreg/audit
chmod 700 /local/bulkreg/ids /local/bulkreg/secure /local/bulkreg/cert
# If SELinux is Enforcing and Domino runs confined, check: ls -Z /local/bulkreg ; ausearch -m avc -ts recent

Option 2 – helper script (does the same, and also copies the config templates)

Windows:  .\scripts\windows\bulkreg.cmd Init            (add -ServiceAccount DOMAIN\svc-domino for Mode B)
Linux:    sudo DOMINO_USER=notes DOMINO_GROUP=notes ./scripts/linux/bulkreg.sh init
Done when
The five folders exist. ids, secure and cert are not readable by Everyone/Users (Windows) or by other users (Linux: mode 700).

6. Step 4 – Build the Tool Database (bulkreg.nsf)

Who: Domino administrator with Domino Designer. Changes: creates one new database.

  1. Create a blank database bulkreg.nsf: on the admin workstation (Mode A) or on the registration server (Mode B). Set its ACL to administrators only.
  2. Optional: create bulkreg_log.nsf from the Agent Log template (alog4.ntf) for central logging.
  3. In Designer create a LotusScript library named exactly BulkRegCommon, then paste in BulkRegCommon.lss.
  4. Create four LotusScript agents and paste in the matching .lss file. Names must match exactly: 01 | Preflight Check, 02 | Export to Registration Text File, 03 | Bulk Register (ID Vault), 04 | Verify Registration + Vault.
  5. In each agent's (Options) section, keep Option Public, Option Declare and Use "BulkRegCommon".
  6. Set the agent properties for your mode (table below), save, check for compile errors, and sign with the admin ID.
Agent propertyMode A – Windows clientMode B – Domino server (Windows / Linux)
TriggerOn event → Action menu selectionOn schedule (for example Daily). Run on: the registration server.
TargetNoneNone
Runtime security–Allow restricted operations (needed for file I/O and notes.ini)
Run on behalf of–Admin identity with directory rights. The signer needs unrestricted agent rights in the Server document.

How to start an agent (used in Steps 5–9)

ModeAction
A – Windows clientOpen bulkreg.nsf → Actions → choose the agent. Enter the config path when asked (it is remembered).
B – Domino serverServer console: tell amgr run "bulkreg.nsf" '01 | Preflight Check'. Use the same pattern for 02/03/04. The agent refuses to start while ServerRunEnabled=0, so set it to 1 before the run and back to 0 after.
Done when
The library and all four agents compile without errors, the database is signed, and the ACL is limited to admins.

7. Step 5 – Run Preflight (Agent 01)

Changes: none (read-only). Mode B: set ServerRunEnabled=1 first.

  1. Start 01 | Preflight Check.
  2. Read the summary: Environment errors, and OK / WARN / ERROR per user.
  3. Open the newest BulkReg_Preflight_<run>_audit.csv from the audit folder (Audit Viewer, Excel, or status helper).
  4. Fix every ERROR. Typical causes are a missing LastName, an unreachable home server, or a duplicate ShortName or InternetAddress. Fix the data in AD and let DirSync re-sync, then run Preflight again.
Done when
Environment errors = 0 and user ERROR = 0. Every WARN has been reviewed and accepted.

8. Step 6 – Dry Run (Agent 03, DryRun=1)

Changes: none (simulation).

  1. Confirm DryRun=1. Start 03 | Bulk Register (ID Vault). In Mode A, answer Yes to the summary.
  2. Open the BulkReg_Register_<run>_audit.csv. Every user shows WOULD_REGISTER, with the HomeServer, OrgUnit and Policy they would get.
  3. Check the mapping result for a sample of users in each region or department.
Done when
Every WOULD_REGISTER row has the intended server, OU and policy. The dry-run audit CSV is attached to the change ticket.

9. Step 7 – Pilot: Register 2 Users

Changes: registers 2 users.

  1. In bulkreg.ini set ExtraSelection=ShortName = "pilot1" : "pilot2", BatchSize=2 and DryRun=0.
  2. Mode A: start Agent 03, answer Yes, then type REGISTER. Enter the certifier password if UseCA=0.
  3. Mode B: set ServerConfirm=REGISTER-<yyyymmdd> (today's date on the server), then tell amgr run "bulkreg.nsf" '03 | Bulk Register (ID Vault)'.
  4. Check both users by hand. The Person document has a Certificate and a hierarchical name. Mail system is still Other Internet Mail. The user can download the ID from the vault and log in.
  5. Start 04 | Verify Registration + Vault.
Done when
Both pilot users show REGISTERED with vault status IN_VAULT, and the manual checks pass.

10. Step 8 – Register in Batches

Changes: registers users.

  1. Clear ExtraSelection (or set it to a department/region wave). Set BatchSize (start with 25–50 and increase after clean runs).
  2. Start Agent 03 (Mode B: today's ServerConfirm is required). Each run takes only users who are still unregistered.
  3. After each run, review the totals: REGISTERED, FAILED, REGISTERED_VAULT_PENDING. Fix the causes (chapter 15) before the next batch.
  4. Repeat until Preflight or Verify shows no UNREGISTERED users in scope.
  5. If the run stops with Circuit breaker, the same error repeated. Fix it, then simply run again.
Note
Keep each batch short enough to finish within the Agent Manager maximum execution time (Server document) in Mode B. Allow time for directory and vault replication between batches.
Done when
All in-scope users are REGISTERED, or listed as accepted exceptions.

11. Step 9 – Verify and Close

  1. Start 04 | Verify Registration + Vault. Re-run it against another vault replica by changing VaultServer if you need to confirm replication.
  2. Hand over initial passwords through an approved secure channel. Users must change them at first use.
  3. Delete temporary secrets only after Verify shows IN_VAULT: the password file and registration text file in secure, and the local ID files in ids.
  4. Set DryRun=1, ServerRunEnabled=0 and clear ServerConfirm.
  5. Archive the audit CSVs and debug logs with the change record and close the change, including totals by result.

Delete secrets manually, or with the helper (it lists the files first and deletes only with --yes / -Yes):

Linux:    shred -u /local/bulkreg/secure/BulkReg_InitialPasswords_*.csv /local/bulkreg/secure/BatchReg_DirSync_*.txt
          shred -u /local/bulkreg/ids/*.id
Windows:  Remove-Item C:\BulkReg\secure\BulkReg_InitialPasswords_*.csv, C:\BulkReg\secure\BatchReg_DirSync_*.txt
          Remove-Item C:\BulkReg\ids\*.id
Helper:   bulkreg.sh purge-secrets --include-ids --yes     |   bulkreg.cmd PurgeSecrets -IncludeIds -Yes
Done when
Verify shows every in-scope user IN_VAULT. Secrets are deleted, the config is back to safe values, and the change is closed.

12.1 Recommendation by mode

ModeDo you need the scripts?
A – Windows clientNot really. Create the folders once (Step 2) and use the Audit Viewer. The PowerShell script is a convenience.
B – Linux / RHEL serverRecommended. Without a desktop, init, check, status, tail and purge-secrets save time and avoid permission mistakes.
B – Windows serverUseful for Init -ServiceAccount (correct ACLs for the Domino service account), plus Check and Status.

12.2 What the scripts add

  • Every config change creates a timestamped .bak copy and prints a diff.
  • Every state-changing command is logged to <AuditDir>/bulkreg_admin_actions.log (time, OS user, host, action).
  • purge-secrets only lists files unless you add --yes / -Yes. ID files are included only with --include-ids / -IncludeIds.
  • run prints the documented console command. It sends the command itself only if you set BULKREG_CONSOLE_CMD to a console wrapper you have verified. HCL 14.x does not document sending console commands from the OS shell.

15. Troubleshooting

To debug: set LogLevel=DEBUG, repeat with DryRun=1 or a 1-user ExtraSelection, then read the debug log. Each FAILED line shows the stage (load, validate, configure, RegisterNewUser, verify, preserveMail, vault), the Notes error number and the code line.

SymptomLikely causeFix
Mode B agent does nothingServerRunEnabled=0, or BulkRegConfigPath not set on the serverarm, or set config BulkRegConfigPath=…. Check the server console/log.
Mode B LIVE refusedServerConfirm missing, or not today's date (server clock)Set ServerConfirm=REGISTER-<today>
Mode B: 'requires UseCA=1'UseCA=0 on a serverUse the Domino CA and list the server as an RA
Audit folder not writableFolder missing, or permissions are wrong for the user/service accountRedo Step 2; on Linux check the owner and SELinux
Preflight finds 0 usersNo objectGUID, already registered, or ExtraSelection too narrowCheck a Person document's properties; clear ExtraSelection
FAILED stage=RegisterNewUserNot an RA, wrong CertifierName or password, or missing rightsDebug log message; fix the CA/RA or the rights
REGISTERED_VAULT_PENDINGPolicy has no vault, wrong policy name, or replication delayCheck the policy synopsis; re-run Agent 04 later
Duplicate ShortName / InternetAddressCollision in AD or the directoryFix in AD, re-sync
MailSystem changes after the next syncDirSync attribute mappingAdjust the DirSync mapping, or set PreserveMailSystem=0
Run stops: Circuit breakerThe same error repeatedFix the cause and re-run (safe)
Linux: config values ignoredWindows CRLF line endssed -i 's/\r$//' bulkreg.ini (the check command detects this)

Escalate to the platform owner if failures affect more than one batch. Escalate immediately to the security owner if a password file, ID file or certifier may have been exposed. Do not try to fix that yourself.

16.3 Rollback

Registration certifies the existing Person document and creates an ID. It cannot be cleanly undone, which is why Steps 5–7 exist. To reverse a user, identify them from the audit CSV and use your standard deletion process (AdminP Delete Person) and vault clean-up. HCL notes that users registered through user registration are not removed by a DirSync full resync. To recover from an interrupted run, just run it again.

Appendix A – Alternative Methods (Manual)

A.1 Register Selected Person (small numbers)

Domino Administrator → People & Groups → select DirSync users → right-click Register Selected Person → choose the certifier and the ID-Vault policy. You are prompted once per user. Run Agent 04 afterwards.

A.2 Registration text file (Agent 02 + Import)

  1. Run Agent 02. It writes secure/BatchReg_DirSync_<run>.txt (UTF-8 with BOM, ;-separated, CRLF). The file contains passwords.
  2. Domino Administrator (Windows) → People → Register → choose the ID-Vault policy → Import Text File → Register All.
  3. Run Agent 04, then delete the file.
Caution
HCL documents the text-file import for new users. Test 1–2 DirSync users first. If you get duplicate entries, use the main method (Agent 03).
