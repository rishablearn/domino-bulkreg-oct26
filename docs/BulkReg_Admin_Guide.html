Rules

  • 03 only accepts a batch file built by 02. It never selects users by itself. There is no 03 without 02.
  • Always run 03 twice per batch: first with DryRun=1, then with DryRun=0, on the same batch file.
  • One LIVE run per batch. After it, the batch is DONE and 03 refuses it. Users not registered (FAILED, NOT_PROCESSED) are picked up again by the next 02.
  • 01 before 02 the first time and whenever AD data, server_mapping.csv or servers changed. Otherwise it is recommended before each batch.
  • 04 after every LIVE run, and again later for users that were still pending (vault, mail file or cluster replicas).
  • Batch size 1000 (BatchSize=1000): one batch fills about one numbered mail folder. 2500 users = 3 batches (1000 + 1000 + 500).
  • Only one batch open at a time is the simplest way to work. 02 never puts a user into two open batches.
  • 05 is never part of this sequence.
  • DryRun only affects 03 (D3b). Every agent writes to the central log database (B15).

Part A – Understand

A1 What BulkReg does

Directory Sync (DirSync) copies Active Directory users into the Domino Directory (names.nsf) as Person documents. These users can be found in Domino, but they have no Notes ID, no certificate and no mail file (Mail system: Other Internet Mail).

BulkReg turns them into full Domino users, in reviewed batches. Each user gets a certified Notes ID, which is stored in the ID Vault, and a Domino mail file on the right home server. The Person document then points to that mail file. If the home server belongs to a mail cluster, a replica of the mail file is created on every other cluster member (for example the DR servers). Every step is logged for audit.

It uses HCL's documented API for this case, NotesRegistration.ContactNoteID: “Used to register users who have existing Person documents created by syncing Active Directory users into the Domino directory.” The existing Person document is upgraded in place, so no duplicate is created.

B12.3 How a rule matches

  1. BulkReg reads the field named in MatchField from the user's Person document. If the field has several values, the first one is used.
  2. Both the field value and the pattern are compared without regard to upper/lower case.
  3. The pattern may contain * (any text, also none), ? (exactly one character), # (one digit) and [a-l] (one character from a range). Without these the value must match exactly.
  4. If it matches, this rule is used and the following rules are ignored for this user.

B12.5 Order, defaults and the catch-all

  • Order matters: put exceptions and the most specific rules at the top, general rules below.
  • Catch-all last: end with *;*;<server>;;;;; so that every user is mapped. Without it, unmatched users get the Default… values. Preflight warns about this.
  • Empty column: use the default from bulkreg.ini (for ClusterReplicas: automatic). Hyphen `-`: explicitly none (OrgUnit, Policy, Groups, ClusterReplicas).
  • No placeholders: a rule that still contains <…> stops every agent with a message naming the line.

Example (B12.7): a user on DominoADMail/Demo (DC) gets mail1\smith.nsf on DominoADMail/Demo and replicas on DominoADMail2/Demo (DC), DominoADMailDR1/Demo and DominoADMailDR2/Demo (DR).

Why names and folders are shared by the whole cluster

Each member holds every mail file, so mail1\smith.nsf must mean the same user on all four servers. BulkReg therefore treats the cluster as one mail namespace: a name taken on any member (or by a Person document whose mail server is a member, or by an open batch) is taken for the whole cluster, and the numbered folders are filled once (a replica is counted once). Users of the second home server simply continue in the next free folder (B12.7 table).

  2. In Domino Administrator, open the home server's Files tab and select those users' mail files (Ctrl+click).

  3. In Domino Administrator, People & Groups > People, select the wrongly named user(s) and choose Tools > People > Delete. In the Delete Person dialog choose to delete the mail file and all its replicas. Confirm. Result: AdminP removes the Person document, the name from groups, and the mail file and its replicas (check admin4.nsf until the requests are processed).
  4. Check the ID Vault: once AdminP has processed the deletion, the wrongly named ID must no longer be in the vault (as vault administrator, open the vault database from Configuration > Security > ID Vaults). Remove it there if it is still listed. Delete the user's ID file from C:\BulkReg\ids and the line from the password file.
  5. Wait for the next Directory Sync cycle (or start it). Result: the user's Person document is created again from AD, with objectGUID and without Certificate.
  6. With release 3.5.0 installed and CertifierName=/Demo: run 02 - Build Batch for these users (ExtraSelection), check the NotesName column (Neha Arora/Demo), dry-run, then register.

D8 Rollback

Registration certifies the existing Person document and creates an ID. It cannot be cleanly undone, which is why the dry run and the pilot exist. To reverse users, take them from BATCH-<id>_results.csv and use your standard deletion process (AdminP Delete Person) and vault clean-up. HCL notes that users registered through user registration are not removed by a DirSync full resync. To recover from an interrupted run, build a new batch: the unregistered users are offered again.

Run these commands on the machine that holds the kit repository (Terminal on macOS, or PowerShell with Git for Windows).

# one time: connect the folder to your existing private repo
git remote add origin https://github.com/<org-or-user>/<repo>.git
git fetch origin
git push -u origin main            # empty repo
# repo created with a README/LICENSE:
git pull origin main --allow-unrelated-histories --no-rebase -X ours -m "Merge GitHub initial commit"
git push -u origin main

# every change
git add -A
git commit -m "Describe the change"
git pull --rebase
git push

# on the admin workstation: get updates
cd C:\BulkReg-kit
git pull
Caution
Never copy anything from C:\BulkReg (configs with real values, batch files, ID files, passwords, logs) into the kit repository. .gitignore blocks the usual file names, but treat it as a safety net only.
